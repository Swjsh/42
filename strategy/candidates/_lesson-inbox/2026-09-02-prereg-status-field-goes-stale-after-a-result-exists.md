## Candidate lesson: prereg `status` field goes stale after a companion result exists — causes real duplicate compute waste

**Symptom:** `prereg_hygiene.py` (and, worse, a live human/Opus adjudication pass reading it) treated `prereg-pdt-blocked-counterfactual-2026-08-11` as never-run and RE-RAN it from scratch on 2026-09-02 — building a new script (`pdt_blocked_counterfactual.py`), a fresh 28-test guard suite, and a full replay — when a completed verdict (`pdt-blocked-counterfactual-2026-08-11-results.json`, ran 2026-08-11, same FAIL-all-gates conclusion) already existed on disk. Two more preregs (`recency-qty-clamp-2026-08-11`, `ladder-vwap-2026-08-11`) were similarly mis-adjudicated that same night — not re-run, but reasoned about from scratch as "outstanding" or "PARK, speculative" when a real numeric verdict already sat one file over.

**Root cause:** a prereg JSON is a frozen commitment (`status: FROZEN_...`) written BEFORE any outcome. When the study runs, the convention across this repo's research history has been to write a SEPARATE `*-results.json` file carrying the verdict — but **nothing ever writes back to the original prereg's own `status` field.** So the prereg forever reads `FROZEN_BEFORE_RUNNER` / `FROZEN_PENDING_RUN` even after it has, in fact, run and been decided. `prereg_hygiene.py`'s flag logic (and any human/LLM skimming `prereg_hygiene.json`'s `entries[].status`) had no way to tell "genuinely never run" apart from "ran weeks ago, status field just never got the memo."

**Fix shipped 2026-09-02:** `prereg_hygiene.py` now cross-references every prereg against every `*.json` in `analysis/recommendations/` via three signals — `rule_id` equality, a result's `registration` field naming the prereg by filename, and the observed filename convention (strip a leading `prereg-`, append `-results.json`) — with self-match explicitly excluded (a prereg carrying its own `rule_id` with no separate result must not match itself). A matched prereg is never flagged as "never run" regardless of its stale status text, and a new `stale_status_but_has_results` report key surfaces exactly the reconciliation candidates so a future pass reads the real verdict instead of re-deriving or re-running it. Guard: `backtest/tests/test_prereg_hygiene_results_detection_2026_09_02.py` (7 tests, RED-proofed).

**What this doesn't fix:** the SOURCE prereg files' own `status` field is still stale text (left untouched deliberately — a prereg is a frozen artifact and editing its content post-hoc, even bookkeeping, felt like the wrong instinct without a broader policy decision). The monitor now compensates for that at read time, but a human/LLM opening the raw prereg JSON directly (not through the monitor) will still see the old status. Worth a follow-up policy call: should completed preregs get a `result_file` pointer field appended (never changing status/verdict content), the way sibling `-results.json` files already self-report `registration`?

**Generalizable rule for OP-25 encoding:** *any two-file producer pattern (a frozen input + a companion output file) needs either (a) a write-back pointer from input to output, or (b) a monitor that actively cross-references both — never assume a human/LLM will grep for the sibling file before trusting a status field.* This is the same shape as the `trades-enriched.jsonl` no-scheduled-producer gap and the `analysis/self-audit/new-gaps-flagged.md` DONE-marker pattern already in this codebase — a third instance of "the state a monitor reads is not the state that answers the question a human actually has."

**Suggested L## anchor bucket:** C7 (silent success is failure — audit outputs, not exit codes / stale monitors, the L298 class) is the closest existing bucket; this is arguably a sibling to L298 itself rather than a wholly new theme.

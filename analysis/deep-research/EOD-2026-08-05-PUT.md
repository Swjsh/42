## 3. Why risky-1 got out — the chain

**TP1 is the gate that unlocks every downstream protection.**

**When TP1 fires (risky-1):**
1. `12:09:04` ask 2.68 ≥ 2.535 → SELL_PARTIAL 3, fill 2.62
2. same tick → `RATCHET_STOP` runner→BE (1.69), **`profit_lock_armed = True`**
3. `12:10:06` trailing mode → stop = hwm 2.68 × 0.85 = **2.278**
4. `12:17:04` bid 2.01 ≤ 2.278 → SELL_ALL 2, fill 2.03

**When TP1 never fires (risky-3, safe-2):**
- `tp1_filled` stays False all trade
- `profit_lock_arm_scope = "post_tp1"` → **the lock cannot arm**
- `pre_tp1_be_floor_arm_pct = None` → isolated BE floor inert
- structure stop needs a closed 5m bar above 772.33 → **max close 772.125, 20.5¢ short. Never eligible.**
- ribbon-flip needs stack = BULL for a put → **ribbon went BEAR at 12:01 and stayed BEAR**
- → **only the −50% cap remains.** It fired at 14:05 / 14:12.

> **This was predicted verbatim.** `accounts.json` risky-1 `exit_profile_doc`, written **2026-07-29**: *"the registry's +100% TP1 is effectively unreachable on 0DTE, which means the TP1-partial mechanism never fires AND the post_tp1-scoped profit lock never arms — the 2026-07-28 Bold trade peaked +56% with zero protection by design and closed −42%."* 08-05 is that incident replayed at +63% → −50%.

## Two new defects found

### 🚨 A. `CORE-TP1-DISPLAY-DIVERGENCE` — HIGH visibility / **zero money**

safe-2's 11:48 exec row journaled **`"tp": 2.5`** while the armed TP1 was **3.26** — a **30% understatement**.

- **Root cause:** `heartbeat_core.py:2049-2052` computes the *displayed* tp from `params.json tp1_premium_pct` (0.5); `:2224-2230` then arms from the `ribbon_ride` registry (1.0). Lines **2250-2257 already back-correct** `stop`, `premium_stop_pct`, `stop_display`, `stop_mode`, `trigger_level` from the resolved `ExitState` — **`tp` was simply left out of that block.**
- **Why it matters:** this is the exact field you read to answer *"why didn't TP1 fire?"*. **It is what made the parent brief's premise wrong.** It is also a core-vs-fleet parity gap — the fleet path logs `tp1_premium_pct` straight off the shape and is **correct**.
- **Money impact:** none. Both fields are log-only (`_place_simple_entry` takes only symbol/qty/limit_price).
- **Fix** — mirror the existing stop pattern inside the same block:
  ```python
  plan["tp1_premium_pct"] = _exit_state.tp1_premium_pct
  plan["tp"] = round(_exit_state.entry_premium * (1.0 + _exit_state.tp1_premium_pct), 2)
  ```
- **Guard:** assert a core ribbon entry journals `tp == entry*2.0` and `tp1_premium_pct == 1.0`; RED-proof by reverting the two lines. **Revert:** delete them.
- **Status: NOT SHIPPED BY THIS LENS — deliberate.** `heartbeat_core.py` is the hot shared surface and sibling lens-agents are working this same tree this session; a mid-audit edit risks absorbing another lane's work (L271). Handed up as **READY-TO-SHIP** with the exact diff.

### ⚠️ B. `SAFE2-PHANTOM-FLAT-PRUNE` — MEDIUM state integrity / **zero money this trade**

At **13:57:03** the exit pass read `open_qty=0` for safe-2's still-open 3-lot, emitted **`FLAT_PRUNED`, and deleted the exit-state record**. The position sat **unmanaged for ~10 minutes** (10 missed ticks) until **14:07:03**, when `_adopt_untracked_positions` re-adopted it as `strategy="adopted_manual", exit="cap_only"`. From 14:08 the ledger shows **`stop_mode="premium"`, `trigger_level=null`** — structure stop and ribbon-flip exit both silently dropped.

**It was never flat:** same position shows `open_qty=3` at 14:08:03 and sold 3 at 14:12:03. Classic C11 / L237 — two broker READ endpoints transiently disagreeing.

**Zero P&L impact on 08-05, verified three ways:** (a) structure stop was never eligible (max close 772.125 < 772.33); (b) ribbon was BEAR 12:01→close so the `adopted_manual` flip-suppression cost nothing; (c) the −50% cap survived at the identical anchor (0.815 before and after).

**Why it still matters:** a transient `qty=0` can strip a position's structure stop and downgrade it to cap-only with **no error, no warning, no STATUS entry**. `exit_actuator.manage_tick` prunes on a **single** `qty<=0` read. On a day where the 5m close *did* break the trigger, this is a real loss. Suggested fix (needs its own blast-radius pass — `exit_actuator` is shared by `heartbeat_core` **and** `fleet_live`): require two consecutive `qty<=0` reads before pruning, and log loudly whenever a re-adoption downgrades `stop_mode`. **Reported only.**
